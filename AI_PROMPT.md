## 1. Чёткие критерии правильного бронирования

Доказать тестами:

- В пределах **одной** комнаты интервалы не пересекаются. Соседние `[10:00, 11:00)` и `[11:00, 12:00)` допустимы. Брони в **разных** комнатах независимы.
- `end > start`, длительность **15–240 минут включительно**, кратность длительности **15 минутам**; начало и конец на сетке 15 минут **по местному времени офиса**, а не по часам в строке клиента.
- Полный интервал, включая конец, укладывается в **09:00–20:00** местного дня офиса. Начало 09:00 и завершение 20:00 разрешены. Время `office.timezone`: `Europe/Moscow` или `Asia/Novosibirsk` — бери из связанной записи, не вычисляй по ID комнаты.
- Клиент отправляет ISO 8601 **с явным UTC-смещением или `Z`**. Любое корректное смещение обрабатывается как абсолютный момент времени; строки, означающие один интервал, должны работать одинаково. Отклоняй неверные даты, строки без смещения, ненулевые секунды/микросекунды, разрушающие 15-минутную сетку. Не используй `Carbon::parse` как единственную валидацию. При выборе строгого парсера проверь, что он не отвергает корректные форматы, которые требует README.
- `user_id` нового бронирования задаётся **только аутентифицированным пользователем**; переданный клиентом ID, `id`, timestamp и другие поля не имеют власти над сохраняемыми полями. Удалять может только создатель. Проверить `401` без токена и единообразный `403` **либо** `404` для чужой записи; если выбираешь `404`, это предотвращает раскрытие существования объекта.
- Ошибки неверных полей, времени, длительности и конфликта — информативный `422` с полями/причинами. Не допускать превращения ввода пользователя в `500`. Не добавлять бизнес-ограничений на прошлые даты, выходные, праздничные дни или предельный горизонт.
- Проверять **реальное поведение PostgreSQL**, не переносить рассуждения на SQLite. Хранить и сравнивать моменты последовательно: одна договорённость об UTC, локальная временная зона только при проверке рабочего дня. Не путать `timestamp without time zone` и `timestamptz`.

## 2. Известные места риска: проверь и исправь минимально

### A. SQL-инъекция через строковую интерполяцию в `store()` — предварительно CRITICAL

**В исходном архиве было:**

```php
$conflict = DB::select("SELECT id FROM bookings
    WHERE room_id = {$request->room_id}
    AND starts_at <= '{$request->ends_at}'
    AND ends_at >= '{$request->starts_at}'");
```

Пользовательские данные встроены в SQL. Это требует устранения **независимо от того, можно ли превратить конкретную инъекцию в успешное создание записи**. Не считай SQL-инъекцией неизменяемый `orderByRaw('starts_at DESC')` в `index()` — пользовательский ввод там не участвует.

**Предпочтительное направление, не готовый патч:**

```php
$occupied = Booking::query()
    ->where('room_id', $room->id)
    ->where('starts_at', '<', $endUtc)
    ->where('ends_at', '>', $startUtc)
    ->exists();
```

Это параметризованные условия, `exists()` не загружает все строки. Проверь реальные типы `$startUtc/$endUtc` и формат биндинга дат. Не создавай QueryRepository ради одного запроса. Приложи тест, подтверждающий, что вредоносные значения не приводят к SQL-выполнению и не дают `500`.

### B. Mass assignment / подмена владельца — предварительно CRITICAL

**Было:**

```php
$booking = Booking::create($request->all());
```

В исходном `Booking` поле `user_id` доступно для заполнения. Авторизованный клиент может попытаться записать бронь на другого пользователя.

**Возможная правка после валидации:**

```php
$booking = Booking::create([
    'room_id' => $room->id,
    'user_id' => $request->user()->id,
    'title' => $data['title'],
    'starts_at' => $startUtc,
    'ends_at' => $endUtc,
]);
```

Используй только проверенные поля; не дублируй защиту бессмысленными слоями. Проверь тестом `user_id` другого пользователя и посторонние атрибуты. Если решишь убрать `user_id` из `$fillable`, перепроверь способ сохранения и фабрики.

### C. IDOR: удаление чужой брони — предварительно CRITICAL

**Было:**

```php
public function destroy($id)
{
    Booking::findOrFail($id)->delete();
    return response()->noContent();
}
```

**Минимальный вариант при существующем `/api/bookings/{id}`:**

```php
public function destroy(Request $request, $id)
{
    $request->user()->bookings()->findOrFail($id)->delete();
    return response()->noContent();
}
```

Доведи сигнатуру/типизацию до принятых в проекте стандартов. Для implicit binding `Booking $booking` параметр маршрута должен называться `{booking}`, иначе биндинг может быть неправильным. Выбирай ровно один подход; не создавай Policy только ради одной проверки, если это не упрощает реальное решение. Тесты: своя бронь, чужая бронь, отсутствующая бронь, анонимный запрос. Убедись, что API не раскрывает данные постороннему.

### D. Ошибочные пересечения — предварительно MAJOR

**Было:** `starts_at <= :newEnd AND ends_at >= :newStart` — ложно считает встречи впритык конфликтом.

**Нужно:** `starts_at < :newEnd AND ends_at > :newStart`, то есть полуоткрытые интервалы `[start,end)`. Протестируй совпадение, вложение, пересечение слева/справа, касание границ и независимые комнаты. Проверяй эту логику после нормализации к UTC.

### E. Валидация, часовой пояс, длительность, шаг — предварительно MAJOR

**Было:**

```php
$start = Carbon::parse($request->starts_at);
if ($start->hour < 9 || $start->hour >= 20) {
    return response()->json(['error' => 'Нерабочее время'], 422);
}
```

Проверяется лишь начало и часы исходного смещения; нет строгой проверки обоих концов, длительности и 15-минутной сетки.

**Рекомендуемый алгоритм (доработай с проверкой крайних случаев):**

1. Валидируй `room_id` (существующая комната), `title` (непустая строка, длина в пределах БД), `starts_at`, `ends_at` (полноценные ISO 8601 со смещением/`Z`). Неверный формат → `422`, без неотловленных исключений. Не принимая всё через `$request->all()` для записи.
2. Создай **immutable** моменты времени (или аккуратно работай с clone), сравни **timestamps**. Проверь `end > start`, `900 <= durationSeconds <= 14400`, `durationSeconds % 900 === 0`; учти секунды/дробные секунды и границы.
3. Переведи **обе** границы во временную зону `$room->office->timezone`; убедись, что начало и конец находятся на местной 15-минутной сетке, относятся к одному локальному рабочему дню и помещаются в окно 09:00–20:00. В частности, `11:00+04:07` → `09:53 Europe/Moscow`, это **не** валидная локальная 15-минутная точка, хотя само значение ISO корректно.
4. Создай нормализованные UTC-значения для SQL-поиска и записи. Проверь round-trip при `app.timezone`, PostgreSQL `timestamp without time zone` и casts модели. Избегай неявных преобразований часовыми поясами драйвера.
5. Возвращай `422` при логической ошибке/занятом интервале. Не вводи дополнительных правил, которых нет в тестовом.

**Предпочтительная простота:** один контроллер с читаемыми локальными переменными и небольшими проверками; если он действительно становится трудночитаемым, разрешается **один** небольшой обоснованный helper/метод, а не сервисная иерархия. Не добавляй ручные regex и глобальные timezone-хелперы, пока не проверена более простая штатная валидация.

### F. Конкурентная запись — БОНУС, не обязательная часть

При схеме `exists()` → `create()` без синхронизации два запроса могут увидеть свободный слот. Если реализуешь бонус, **докажи на реальном PostgreSQL**, что защита работает.

**Предпочтительный кандидат:** внутри одной `DB::transaction()` сначала загрузить/заблокировать **существующую строку комнаты** через `Room::query()->lockForUpdate()->findOrFail($roomId)`, затем выполнить `exists()` и `create()` **в этой же транзакции**. Оба запроса на одну комнату должны проходить через один протокол блокировки. Не пытайся блокировать отсутствующие записи в `bookings` как единственный механизм.

**Альтернатива:** PostgreSQL exclusion constraint для пересекающихся диапазонов. Она жёстче гарантирует инвариант БД, но добавляет миграцию, особенности диапазонов/расширений и обработку SQLSTATE. Выбирай её **только если реально оправдана**. Не добавляй обе защиты без причины. Если бонус нельзя надёжно реализовать и проверить, README допускает описать решение без внедрения — честно выбери этот путь.

**Проверка гонки:** два отдельных процесса/соединения и контролируемое перекрытие транзакций, а не два последовательных HTTP-запроса или один тест `assertDatabaseCount`. Проверяй, что при одновременных запросах появляется **одна** бронь, а второй получает ожидаемый отказ. Учитывай реальные таймауты/дедлоки, но не вводи retries «на всякий случай».

### G. Дефекты `today()` / `index()` — REVIEW ONLY

Исходный `today()`:

```php
return $room->bookings()
    ->whereDate('starts_at', today())
    ->get()
    ->map(fn ($b) => [
        'time' => $b->starts_at . ' – ' . $b->ends_at,
        'author' => $b->user->name,
    ]);
```

- `$b->user` внутри `map()` без eager loading приводит к N+1 при нескольких бронях и отсутствии предзагрузки;
- `today()` и `whereDate(starts_at, ...)` не учитывают «сегодня» в зоне **офиса**; `whereDate` может усложнять использование индекса, но рост времени запроса без `EXPLAIN ANALYZE` **не подтверждён**;
- событие, начинающееся на границе локальных суток, требует аккуратной семантики «на сегодня» — отдельно объясни, что именно делает исходный код и где ошибается, не придумывая дополнительное ТЗ;
- `index()` использует постоянный `orderByRaw('starts_at DESC')`: это **не SQL-инъекция**. Проверь сортировку/пагинацию/фильтрацию и опиши лишь реальные замечания.

**Не менять тела `index()` и `today()`** и не переписывать тесты, чтобы скрыть исходные недостатки. В `REVIEW.md` дать конкретное минимальное предложение: eager loading `with('user:id,name')`, фильтрация по UTC-границам местного дня вместо `whereDate()` — исключительно как рекомендацию, не реализацию.

### H. Производительность, индексы, прочее

- В `store()` используй один `exists()`, не `SELECT *` и не загрузку коллекции ради проверки наличия; в затронутых местах проверь количество SQL-запросов и случайный N+1 при доступе к `office`.
- Композитный индекс `(room_id, starts_at)` — **кандидат на оптимизацию**, а не доказанное узкое место. Проверь существующие ограничения, объём данных, характер выборок и `EXPLAIN (ANALYZE, BUFFERS)` в репрезентативном окружении; не добавляй несколько индексов «для солидности». Для маленького тестового разумно оставить его без миграции и описать как возможное развитие.
- `Booking::create()` должен оставаться совместимым с существующими фабриками, сидером, модельными casts и API-ответом. Сохрани действующее полезное логирование; не логируй токены и персональные данные, не делай из простого лога систему аудита.
- В миграции используются `$table->timestamp(...)`: выясни, как фактически представлены времена в PostgreSQL, не рассчитывай на автоматическую нормализацию ISO со смещением при записи в `timestamp without time zone`. Если меняешь миграцию, обоснуй влияние на старые записи, сиды и тестовую БД.

- Демо-токены из сидера задокументированы как намеренные. Не выдавай их за критическую production-уязвимость тестового стенда. Если заметишь другие проблемы, отделяй подтверждённые от предполагаемых.

## 3. Как писать код: Ponytail + анти-нейрослоп

Следуй правилам Ponytail: **сначала понять весь затронутый поток**, затем найти самый дешёвый по сложности корректный вариант. (6) можно ли решить простым понятным изменением? (7) только после этого писать новый код.

**Запрещено по умолчанию:** `BookingRepository`, `BookingService`, слои DTO/Mapper/Strategy, интерфейсы для одного класса, собственная date/time-библиотека, новые зависимости, десятки микрометодов, универсальные валидаторы и фабрики ради двух методов. Исключение возможно только если реальная сложность снизится и это можно объяснить по коду и тестам. Нормальные проверки прав доступа/данных, транзакции и тесты не считаются overengineering.

Не удаляй обязательные атрибуции, лицензии и необходимые технические пояснения. Не пытайся скрыть использование ИИ: README разрешает ИИ и требует честные `AI_NOTES.md`.

**Мера минимализма — не минимальное количество символов, а минимальная сложность:** читаемость, корректность на границах, безопасность, способность объяснить код на собеседовании. Избегай и «идеальной архитектуры» на 15 файлов, и нечитаемого контроллера в одну строку.

## 4. Реализация и тесты — обязательно, не только советы

После сверки проблем внеси минимальные правки. Создай полноценные **Feature-тесты через HTTP** (`postJson`, `deleteJson`, Sanctum actingAs, factories) с `RefreshDatabase`, запускаемые на PostgreSQL.

Покрой как минимум:

1. Успешное создание; корректный владелец/сохраняемые поля; ответ API.
2. Разные комнаты в одно время; соседние интервалы; полное совпадение; частичные пересечения с обеих сторон; новая бронь внутри старой и наоборот.
3. `15`, `240` минут — принять; меньше `15`, больше `240`, 0, отрицательное и некратное `15` — `422`.
4. Локальные `09:00–20:00`, точные границы, начало до 09:00, конец после 20:00, переход через местную полночь, шаг `:00/:15/:30/:45`, секунды/микросекунды.
5. И Москва, и Новосибирск. Одинаковый момент в `Z` и в разных смещениях, включая нецелочасовые и `+04:07` для Москвы. Убедись, что шаг проверяется **после** пересчёта к зоне офиса.
6. Некорректная дата, отсутствующее смещение, пустые `title/room_id/starts_at/ends_at`, отсутствующая комната, SQL-подобный ввод, неожиданные поля, чужой `user_id`.
7. Нет токена → `401`; удаление своей → `204`; чужой/несуществующей → выбранный корректный `403/404`; удаление анонимом → `401`.
8. Прошедшая дата при соблюдении прочих требований **разрешена**; нет запретов на выходные.
9. Совместимость с существующим `BookingIndexTest` и модельными отношениями.
10. Если бонус реализован — **отдельный конкурентный сценарий на PostgreSQL с независимыми соединениями**, а не последовательные запросы.

Используй data providers, если реально сокращают повторение без усложнения. Не пиши искусственные десятки проверок ради счётчика тестов; проверяй реальные правила и регрессии. Никаких `sleep()` как единственного доказательства гонки. Тесты обязаны падать на нарушении соответствующего требования, а не просто проверять статус «что угодно».

## 5. Пять проходов независимой самопроверки с исправлением найденного

**Проверка 1 — точность задания.** Снова прочитай README независимо от своих решений. Для каждого пункта укажи файл и тест. Убедись, что `index()`/`today()` **не изменены**, прошлое время не запрещено, API-ответы соответствуют требованиям. Найденное исправь и заново запусти релевантные тесты.

**Проверка 2 — adversarial security.** Посмотри на код как злоумышленник: SQL-инъекция, доверенные поля, невалидные даты, обход авторизации, IDOR, сообщения об ошибках, инварианты БД, гонка. Приведи конкретный сценарий для каждого настоящего дефекта. Исправляй только воспроизведённые/доказанные проблемы. Не называй гипотезу обнаруженной уязвимостью.

**Проверка 3 — time & DB correctness.** Независимо перепроверь чтение/запись `timestamp` с разными смещениями, UTC/локальные границы, шаг, длительность, поведение сериализации Eloquent, одновременные запросы. Если были изменения — повтори полный соответствующий набор тестов **на PostgreSQL**.

**Проверка 4 — performance + Ponytail.** Посмотри на фактические запросы и дифф: N+1 в изменённых путях, лишние запросы, лишние индексы, новые зависимости, `Service/Repository/DTO`, повторные проверки, дублирование кода и тестов. Удали всё, без чего реализация остаётся столь же безопасной, ясной и полной. Оптимизацию скорости заявляй только с замером или планом запроса; не выдавай гипотезу за факт.

**Проверка 5 — anti-neuroslop + строгая приёмка.** Прочитай все изменённые PHP/Markdown-файлы как придирчивый Senior PHP интервьюер. Удали шаблонные и бессодержательные комментарии, декларативные похвалы и объяснения очевидного. Проверь, можно ли без труда устно объяснить **каждую** строку нестандартной логики. Ещё раз сопоставь `REVIEW.md`, `AI_NOTES.md`, README, старый Git-код и фактический diff. После правок — последняя проверка. Не запускай бесконечный рефакторинг: остановись, когда требования доказаны и новые проблемы не найдены.

**По каждому проходу фиксируй краткий результат:** что проверил, что оказалось ошибкой/не ошибкой, какой тест подтвердил, что исправил, что осталось непроверенным. В основной документации не нужны пять многословных отчётов: достаточно итогов в ответе или лаконичного раздела проверки.

## 6. Обязательные артефакты тестового

### `REVIEW.md`

Делай компактную инженерную таблицу/разделы: `файл:метод → critical/major/minor → проблема → точное основание или тест → как исправлено/почему оставлено`. Раздели:

- **исходные подтверждённые дефекты**, устранённые в `store/destroy`;
- **неисправленные по условию задания** дефекты `index/today`;
- **подозрительные, но безопасные конструкции** (например, фиксированный `orderByRaw(...)` без пользовательского ввода);
- **потенциальные улучшения**, которые не являются измеренными проблемами производительности.

Для 4–6 ключевых проблем покажи короткие куски **«Было → Стало → Почему»**, строго по реальному `git diff` (SQL-инъекция, `$request->all()`, удаление без проверки прав, строгие/нестрогие границы, временная зона, при наличии — защита от гонки). Сохраняй исходный код в **истории Git**, приведи реальный базовый hash и способ посмотреть его (`git show <hash>:app/Http/Controllers/BookingController.php`, `git diff <hash>..HEAD`). **Не создавай `BookingControllerOld.php`, не оставляй старые уязвимые фрагменты закомментированными или подключёнными к маршрутам.** Если истории нет, не выдумывай hash; можно вставить лишь короткие подтверждённые исходные фрагменты в `REVIEW.md`.

### `README.md`

Сохрани полезное из исходного README и добавь актуальные команды запуска/тестов **одной-двумя командами**, краткий формат времени и ожидаемые ошибки. Если API теперь игнорирует/не принимает `user_id` из тела POST — скорректируй пример. Если бонус гонки **не реализовал**, по заданию объясни в README, как именно его можно устранить. Не превращай README в учебник или маркетинговый текст.

### `AI_NOTES.md`

Честно перечисли **реальные** AI-инструменты и **дословные** 2–3 ключевых промпта, если их действительно было 2–3. Если фактически использован только этот один большой промпт — не сочиняй остальные; укажи один и обоснуй это. Не выдавай пересказ/сокращение за дословный текст; при необходимости приложи полный текст использованного промпта и прямую ссылку из `AI_NOTES.md`, не маскируя это под «дословную цитату». Опиши реальный случай ошибки/неоптимальной рекомендации ИИ **или** то, что целенаправленно перепроверил. Укажи, какие решения и проверки были выполнены человеком/в инструментах, не делай ложных заявлений о ручной проверке, которой не было.

### История Git

Сохрани исходное состояние и делай **несколько осмысленных, проверенных** коммитов (функциональность, тесты, документация; фактическая разбивка зависит от работы). Ни в коем случае не делай поддельные старые коммиты или `force push`. Не коммить `.env`, `vendor`, логи, секреты, временные файлы. Не пушь в чужую ветку без разрешения. Если работаешь без `.git`, честно сообщи, что историю нужно сохранить в реальном клоне репозитория.

## 7. Реальные команды и критерии завершения

Проверь доступность окружения. В изолированном локальном стенде при необходимости:

```sh
docker compose up -d --wait
docker compose exec app php artisan migrate:fresh --seed
docker compose exec app php artisan test
```

`migrate:fresh` разрушает данные: **используй только на заведомо тестовой/локальной БД**. Для узких проверок запускай `php artisan test --filter ...`; затем обязательно весь набор. При изменении PHP-кода запусти Pint согласно `AGENTS.md` (например, `vendor/bin/pint --dirty --format agent`, если версия поддерживает), `php -l` и `git diff --check`. Проверь реальные exit codes и логи команд. Если исправил что-то после полного тест-прогона, повтори релевантные проверки.

Если недоступны Docker/Composer/PostgreSQL/инструменты — не имитируй успех: скажи, какие команды не запускались, что именно не подтверждено и как это запустить. Особенно не выдавай последовательный тест за подтверждение отсутствия race condition.

**Не объявляй задачу готовой**, пока не сверены все требования README, безопасность/авторизация, 15-минутный шаг в зоне офиса, корректные пересечения, отсутствие лишних слоёв, существующие и новые тесты, `REVIEW.md`, `AI_NOTES.md`, README, неизменность `index/today` и история коммитов (либо честные ограничения среды).
